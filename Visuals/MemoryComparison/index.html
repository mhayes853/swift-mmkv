Where each core's memory goes, key by key

The same stores, opened by the C++ core and by the Swift core, with each core's heap taken apart into what it is made of. The Swift core keeps one fixed-size slot per key in a hash table, plus an arena for an encrypted store's keys and small values. The C++ core allocates a node per key and, for an encrypted store, a buffer per value. Most of what the Swift core still spends is empty slots.

03

How much of the Swift table is empty

A table's capacity is a power of two and it doubles once it is three-quarters full, so it is between 37.5% and 75% full. Loading shrinks it to the smallest such capacity, which for the round numbers measured here happens to be a poor fit at 100,000 keys. Each grid is 64 cells standing for the whole table.

05

Heap growth over 2,000,000 writes

A store of 10,000 keys written 200 times over, which makes each core rewrite its file many times. Measured as the change in anonymous memory from before opening to the end of the loop. Neither core grows as the writes go on. "Other" holds what this measurement can't split: allocator slack, and in the Swift core's encrypted store, arena space waiting to be compacted (it compacts at half garbage).

06

The mapped file, the same in both

Outside the heap, both cores map the store's file, and they write identical bytes to it. Loading reads every record, so every page holding data is resident afterwards in either core.

Plain, 100,000 keys: an 8 MB file
6.0 MB of records, resident after loading2.1 MB not yet written

On a disk, these pages are clean once written back, so the system can drop them, and iOS does not count them against an app. On a tmpfs, such as /tmp on the Linux machine measured here, they are always dirty and show up in private dirty memory, which inflates MemoryReport's Linux footprint column by about the file's size for both cores. The heap figures above don't include them.
