How the Swift core keeps a store's index in half the memory

An MMKV store keeps every key's latest record in a memory-mapped file, plus an index in memory that says where each key's record is. In the C++ core, and in the first Swift port, that index holds its own copy of every key, and each entry costs a heap allocation or two. The Swift core now uses a hash table of fixed-size slots in one allocation. A plain store's slots hold no keys at all and compare against the keys already in the file. An encrypted store's slots point into a single arena of keys and small values. A plain store of 100,000 keys now takes 4.1 MB instead of the C++ core's 8.0 MB, and writes make no heap allocations.

What one key costs

Heap bytes per key in each core's index, for the memory report's store: keys like key-12345 (9 bytes) holding strings of 50 characters (51 bytes stored). The parts are the allocations each index makes, and their totals match what MemoryReport measures at 100,000 keys. Switch to an encrypted store to see the second index.

02

Where those bytes went: a copy of every key

Both earlier indexes kept a copy of every key in a heap allocation of its own, next to a 12-byte record location. But a plain store's record starts with its key, and the file is mapped into memory already, so each key was held twice. The offsets in these pictures are examples.

03

RecordIndex: 16 bytes a key, and no keys

A plain store's index is a SlotTable: one block of slots, using open addressing with linear probing. A slot holds the key's hash and the same 12-byte location the C++ core keeps. The key names shown in grey are for reading the picture; the table doesn't store them.

04

Finding a key the table doesn't keep

A lookup compares 32-bit hashes first, and reads a key from the mapped file only when the hashes match. Pick a key that is in the store or one that isn't. The hashes are examples. The table seeds its hash randomly each time it is created.

05

A write without a heap allocation

A write uses the key's bytes where the String keeps them, encodes the value on the stack, and looks the key up once. Then it appends the record to the file and points the slot at it. Before, the same write made several heap allocations, starting with an array holding a copy of the key. Pick an overwrite or a new key.

06

Removing without tombstones

With linear probing, a removed slot can't just be emptied: keys placed past it would no longer be found. Rather than mark it removed, which leaves scans longer forever after, the table moves the later keys of the run back. This is backward-shift deletion.

07

CryptIndex: one arena for keys and small values

An encrypted store's records are ciphertext, so its index has to keep the keys, and the values it serves from memory. The C++ core gives each key a std::string and each value from 28 to 256 bytes a buffer of its own. CryptIndex packs all of them into one growing block, the arena, with a 20-byte slot per key in the same kind of table. The offsets are examples.

08

Loading an encrypted store a window at a time

The data is one AES-CFB-128 stream. The first port decrypted all of it into a buffer the size of the data and built the index from that. The Swift core now decrypts at most 128 KiB at a time, as the C++ core does, and never decrypts a large value while loading. Records are not drawn to scale.

“Before” was measured only on macOS, before these changes; the Android measurements came after them. The same changes made writes 2.3 to 2.9 times faster: write.string went from 593 ns to 258 ns (171 ns in the C++ core), and write.int32 from 657 ns to 225 ns (143 ns).

What checks itThe file format didn't change: both cores still write the same bytes.
RecordIndexTests
Finds every key it holds and none it doesn't, over 3,000 keys of mixed lengths. It removes keys one at a time and by a condition, checks every key after each step, and checks that a moved record keeps its slot and version. Breaking backward shift fails it with 1,014 issues.
CryptIndexTests
20,000 random operations against a dictionary model, with four seeds. They cover replacements that fit in place, values over 256 bytes, values read from the arena and written back under another key, and compaction.
DifferentialTests
Each core reads the other's files, including an encrypted store more than four windows long, with values of 1 to 2,000 bytes and removals. That test crashes if large values aren't skipped, and it passes with the window forced down to 4 KiB.
MemoryReport
Measures both cores in fresh processes on macOS, and on Android with an Android-only shim for a libc++ symbol the NDK lacks. It fsyncs each copied store first, so that page cache isn't counted as the store's memory.
